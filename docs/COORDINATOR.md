## Separate trust domain

The coordinator is not part of the public web application and does not use its D1 account database. The local deployment model runs it in a dedicated read-only container with only:

- one Ed25519 coordinator private key;
- one file-backed SQLite database on its own volume; and
- network access to the isolated role-specific Lightning adapters and authenticated Ethereum RPC providers.

It receives no LND macaroon, node seed, web session secret, email record, user private key, or solver-inventory withdrawal key. An authenticated public identity is compared to its RFQ only in memory; the database retains an opaque identity commitment and a binding digest, never the raw wallet identity. An optional claim-relayer key may spend only its own capped ETH gas because `claim` is permissionless and its beneficiary is already fixed onchain. The adapters receive only the coordinator public key and one role-specific macaroon. A production deployment must preserve these as distinct hosts, service identities, networks, secret scopes, and backup policies.

## Persistent closed supervisor

The coordinator image no longer starts a smoke fixture and exits. Its default process is `infra/coordinator/service.mjs`, a persistent closed supervisor with no network listener, dispatch authority, funding capability, adapter credential, provider endpoint, or signing key. It opens one absolute durable SQLite path, runs startup recovery and integrity checks, publishes only aggregate mode-`0600` health under a separate mode-`0700` runtime directory, and remains alive until a termination signal. The container health check independently verifies the exact closed schema, fresh heartbeat, database status, lease identity, and false funding authority.

An opt-in `COORDINATOR_MODE=release-verification-only` now exercises the persistent release boundary without adding a listener, solver input, dispatch path, or funding entry point. It requires `COORDINATOR_RELEASE_ACTIVATION_MANIFEST_PATH` in a separate read-only directory, reconstructs every raw input, rechecks five release approvals and two reconciliation signatures, and obtains fresh live RPC quorum state on each bounded refresh. The manifest path and provider URLs never enter health output. The status exposes only digests, block identity, expiry, counters, and five explicit false authorization fields. A failed or expired verification makes container health fail while the process retains its lease and retries.

Every refresh revokes the prior module-private activation before reading new evidence. A failed refresh, malformed result, clock rollback, exact expiry, shutdown, or replacement therefore invalidates new-exposure authorization for every context derived from that activation immediately; copied activations cannot trigger or bypass revocation. The original active context may finish recovery-only work while its process survives. After a restart, recovery requires a new same-process recovery activation rebuilt from the exact raw release evidence, historical five-role approval bundle, current candidate-bound provider set, and fresh canonical runtime quorum. It may operate while the release is expired, the gate is closed or emergency halted, BIT is paused, or reserves are below opening limits, but it grants no funding, new-exposure, or Lightning-dispatch authority. Serialized status never restores provenance.

One fresh filesystem lease excludes a second supervisor. A crashed owner remains fail-closed until its heartbeat exceeds a bounded three-heartbeat stale interval; a stale owner cannot authorize work or refresh itself, takeover is atomic, and a resumed old owner cannot update or delete the successor's lease. The raw lease token remains module-private: the public lease object contains only its digest identifier, start time, directory, and bounded methods. Funded-daemon authorization requires that exact original object and a fresh ownership read; a copy, serialization, fabrication, released lease, stale lease, or replaced owner cannot pass. Relative/overlapping database and runtime paths, symlinks, malformed or future leases, unsafe timing, funding-enabled configuration, authority-bearing status, secret-shaped metrics, and unknown database schema all reject. The database and runtime directories remain separate, and the status never includes invoice, preimage, wallet, address, email, endpoint, macaroon, key material, or lease token.

The default process remains closed, while the opt-in verifier retains a live release only inside its process. Neither mode can create an intent, accept a solver, reserve inventory, call Lightning, broadcast EVM transactions, open the gate, or authorize funding. The funded wrapper now accepts only the verifier's original in-memory activation, original solver capability evidence, original coordinator store, and original live service lease. It rechecks ownership, the current internal clock, packet/evidence expiry, and—on new exposure—live release funding after external reads and immediately before each pre-request or evidence-derived durable mutation. Dispatch paths check both before claiming the outbox and again immediately before contacting Lightning or broadcasting EVM bytes; the Lightning adapter envelope is also rechecked at send time. If leadership or validity is lost after the durable claim, no network request starts and restart recovery conservatively moves that action through `UNKNOWN`. Once a network request has started, its original caller may record only the response or ambiguity needed for safe reconciliation. The packaged service still supplies no solver input or execution loop, and multi-replica funding remains unsupported.

The local same-process funding predicate no longer accepts nominal solver-session flags. It requires the original module-private solver-capability verification and the original active release capability/runtime snapshot pair; then it rechecks exact capability expiry, fresh independently observed capacity, chain, direction-specific escrow address, and escrow runtime code hash against the live release manifest. Copies, cross-release capabilities, wrong-direction contracts, stale capacity, and exact-boundary expiry fail closed. This closes a local authorization gap but does not turn the packaged closed supervisor into a funded activation service.

Schema v7 closes the cross-release restart boundary. Before a funded wrapper may observe or advance a settlement, `bindActiveSolverSettlementExecutionPolicy` atomically commits the accepted settlement to its unique selected firm offer, exact firm-offer capability digest, reviewed release-record digest, daemon-evidence-policy digest, and binding time. It derives those fields only from the original active daemon context, requires the original live service lease and unmodified coordinator methods, and must run before any reservation or action. Exact retries are idempotent; a different release, policy, capability, time, reused selected offer, late binding, method substitution, or incomplete user-authorized quote fails closed. A recovery context may use a newer short-lived capability epoch for the same solver after restart, but the durable settlement continues to require its historical firm-offer capability and original release/policy binding. Schema v6 and older databases with any nonterminal settlement or active firm offer refuse migration because this authority cannot be reconstructed safely.

## Atomic record

`lib/coordinator-store.mjs` binds one private settlement identifier to all of the durable settlement commitments:

- a different unlinkable public pricing identifier;
- direction and nonce-authority digest;
- exact intent nonce and intent digest;
- globally unique payment hash;
- invoice digest and whole-satoshi amount;
- received-quote-set digest, selected-set digest, and selected offer;
- capacity epoch;
- exact selected-offer capability, reviewed release, daemon-evidence policy, and one-time execution-policy binding;
- exact EVM reservation transaction, block, and intent proof;
- one request ID, payload digest, and dispatch count for each value-moving action;
- an EVM claim's chain, sender, contract, nonce, transaction hash, signed-byte digest, broadcast count, and one observed inclusion; and
- one mutually exclusive terminal result supported by a both-assets reconciliation proof.

Schema v7 also persists RFQ/admission state in the same transaction boundary:

- an opaque authenticated identity commitment and permanent cancellation sequence;
- exact request ID, direction, notional, nonce, expiry, and lifecycle state;
- rolling accepted-request and cancellation events;
- a verified solver capability digest and expiry, monotonic capacity epoch, fresh available capacity, committed capacity, and conflict latch;
- one exact firm offer per solver/request, its separate BIT and Lightning capacity commitments, maximum outbound routing headroom, first user-selection authorization digest and expiry, one private-request digest, one executable EIP-712 offer digest, second user-execution authorization digest and expiry, and mutually exclusive outcome; and
- successful fills, attributable failures, consecutive-failure suspension, and aggregate-only metrics.

Admission first expires stale requests and releases their exact commitments, then evaluates persisted usage inside `BEGIN IMMEDIATE`. The first accepted RFQ writes the complete normalized admission-policy digest to coordinator metadata; every later admission, reservation, and outcome must use that identical digest, so a request cannot supply looser caps or failure thresholds. A duplicate request or offer ID is idempotent only for the same committed terms. Cancellation sequences only advance. Lightning → BIT reserves gross solver BIT and inbound Lightning capacity; BIT → Lightning reserves output plus the signed routing ceiling. Two local database connections cannot exceed the active-request limit, oversubscribe either resource, or bind different executable quotes to one offer. There is no solver allowlist: only a locally verified capability and authenticated blind selection can enter firm capacity. Unknown BIT → Lightning solvers receive the configured total outbound exposure cap, including routing headroom, and an atomic global in-flight ceiling spans every solver identity; established capacity requires the configured number of completed settlements. A filled offer exercises its RFQ and releases every competing commitment in the same transaction, but it cannot increment successful history without an exact `COMPLETED` settlement, the same selected offer, and the same independently verified both-assets proof digest. User abandonment and expiry release both resources without harming solver reliability.

Selected-solver disclosure is not authorized by a caller-supplied boolean or copied object. It requires the exact module-private delivery selection, the same locally verified capability used in that book, a verified short-lived EIP-712 user signature over the selection and private request, unmodified coordinator methods, and the exact active firm, RFQ, capacity, and persisted authorization records. Finalization writes the private-request and executable-offer digests once but remains non-authorizing. The exact user must sign the complete executable quote and invoice/hash commitments before schema v7 persists the execution-authorization digest and signed expiry and exposes a module-private executable result. Authorization use rechecks the active durable record and fails at the exact expiry boundary. An exact retry is idempotent; a second approval, hold invoice, payment hash, request, or quote is rejected. Schema v5 and older databases with any active firm commitment refuse migration because the required authorization state cannot be reconstructed safely.

Each transition and its secret-free event commit in one `BEGIN IMMEDIATE` transaction. Every solver-capacity read also recomputes both commitments and the active-offer count from the firm-offer ledger; partial accounting mutation fails closed. Foreign keys, uniqueness constraints, strict tables, WAL journaling, `synchronous=FULL`, a five-second busy timeout, a mode-`0600` database, and a mode-`0700` parent directory are enforced. Startup runs a fail-closed quick integrity and foreign-key check before accepting work, refuses an unknown schema before adding or migrating tables, and exposes a full integrity check for backup and recovery workflows. SQLite serializes independently opened local connections, and adversarial tests cover competing admission, dual-resource capacity reservations, executable-quote races, and ledger divergence. Multi-host or multi-replica operation is not supported by this version.

The pinned runtime is Node `22.22.0`. Its built-in SQLite API remains experimental in that release even though the underlying database and the exact API surface used here are pinned. TreeSwap uses Node's SQLite online-backup wrapper rather than copying a live database/WAL pair. A backup is written to a private temporary file, fully integrity- and foreign-key-checked, synced, copied without overwrite, mode-locked to `0600`, and synced with its directory. Restore verifies the source and writes only to a new path; it never replaces a live database. The prior published pinned-image checkpoint passed schema-v4 parity, v2 migration, fail-closed v3 capability migration, verified backup/restore, corruption refusal, SIGKILL/WAL recovery, and bounded-filesystem `SQLITE_FULL` rollback. Schema v5 passes the expanded 97-test pinned-runtime matrix and the 41-campaign sealed qualification from clean published commit [`b4f10c1604ed2d4c384d05cc1971afc050536533`](https://github.com/bobofbuilding/treeswap/commit/b4f10c1604ed2d4c384d05cc1971afc050536533); its independently reconstructed local-only digest is `sha256:f6c7d23181fcc17989ef6f122ff8f08b52f4eae3b90d72157c1168dfd8397272`. ## Dispatch and recovery

`lib/coordinator-action-runner.mjs` requires the transient operation to hash to the persisted payload commitment before it signs or contacts an adapter. The coordinator then changes `PENDING` to `DISPATCHING` durably before the external call. A request can be claimed once and its dispatch count can never exceed one.

| Observation | Durable result | Automatic retry |
| --- | --- | --- |
| Exact validated success proof | `CONFIRMED` | No |
| Coordinator-local rejection before dispatch | remains `PENDING` | No call occurred |
| Any adapter rejection, timeout, transport loss, replay conflict, or malformed success after durable dispatch | `UNKNOWN` | Never |
| Process restarts while `DISPATCHING` | `UNKNOWN` | Never |
| Read-only `IN_FLIGHT`, `OPEN`, `ACCEPTED`, or `NOT_FOUND` | remains `UNKNOWN` | Never |
| Exact `SUCCEEDED`, `SETTLED`, or method-compatible terminal proof | `CONFIRMED` | No |
| Impossible terminal observation | settlement `HALTED` | No |

An `UNKNOWN` action blocks every later action and every terminal transition. The recovery call uses a fresh signed, read-only `TrackPaymentV2` or `LookupInvoiceV2` request. It compares the returned hash and amount to the durable action before recording the observation. A successful tracked payment must also return a preimage whose SHA-256 is the bound payment hash. That preimage is returned only to the in-memory caller; only its observation digest enters SQLite. A confirmed payment can be queried again with a new signed read-only request after a later restart so the EVM claim can be reconstructed without persisting the preimage. LND REST stream error envelopes are parsed before result validation: a read-only gRPC `NotFound` becomes sanitized `NOT_FOUND`, while a send-stream error remains ambiguous. `NOT_FOUND` is not proof that a value-moving call was never accepted, so it intentionally leaves the action blocked.

### EVM claim outbox

`lib/evm-action-runner.mjs` accepts only an EIP-1559 call to the configured immutable escrow's exact `claim(bytes32,bytes32)` selector. It checks the reservation ID, `sha256(preimage)`, chain, sender, contract, pinned runtime-code hash, nonce, total gas-cost ceiling, fee fields, zero native value, and canonical calldata against the durable action before signing. Chain ID and runtime code are re-read before broadcast, and the code is re-read by canonical block hash during reconciliation. Only the transaction hash and a digest of the signed bytes are persisted; the preimage and signed raw transaction remain transient.

The transaction hash is bound before broadcast. An RPC acceptance, rejection, timeout, or lost response always leaves the action `UNKNOWN`. Recovery may reconstruct and rebroadcast only byte-identical signed transaction data with the same transaction hash; it cannot fee-bump, replace, change the nonce, or change calldata. Reconciliation validates the RPC transaction fields, canonical inclusion block, receipt status, exact escrow address, exact `Claimed` event, and the provider's `finalized` head. The unattended daemon requires exactly two differently labeled provider origins to produce the same normalized observation. Both reads finish before any state mutation; outage or disagreement leaves the action `UNKNOWN`, while exact agreement applies one durable transition. Different origins do not establish independent operators or backends, which remains a deployment evidence requirement. A pending or unfinalized transaction remains blocked. A reverted finalized transaction fails. A disappeared or changed observed inclusion, mutated RPC transaction, or success receipt without the exact event halts the settlement.

The full invoice or preimage is supplied only in memory for an exact dispatch. The database stores its commitment or the resulting proof digest, never the raw value. Metrics expose only aggregate state counts, including EVM outbox state, and the secret-free event view excludes settlement IDs, transaction hashes, payment hashes, addresses, invoices, preimages, and email.
